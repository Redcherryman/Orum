# Orum v0.013 — current language and compiler status

Orum is a statically checked language with a Python bootstrap compiler
that emits native x86-64 ELF executables. This note records the
implementation at v0.013; it describes the current compiler rather than
claiming complete, production-quality support.

## Whitespace and block rules

Spaces, tabs, and indentation do not define blocks and never change a
program's meaning. Whitespace may be used freely between tokens,
including around calls, operators, and delimiters. Blocks are opened by
constructs such as `fn`, `if`, `while`, `for`, `match`, `struct`, and
`asm`, and closed by explicit `end` keywords (`else` separates branches).

A physical newline terminates a statement outside parentheses and square
brackets. Newlines inside parentheses or square brackets are ignored,
so expressions and argument or element lists can span lines. Layout is
flexible, but statement boundaries remain explicit.

## Implemented language features

- Integer literals and signed/unsigned 8-, 16-, 32-, and 64-bit integer
  types, with `int` as the signed 64-bit default.
- Immutable-by-default bindings and explicit `mut` bindings/parameters.
- Functions, recursion, structs, function-pointer types/calls, and
  two-option tagged unions with `ok`/`err` construction and `match`.
- `if`/`else`, `while`, integer-range `for`, and list iteration.
- Arithmetic, comparisons, bitwise operators, and shifts.
- Strings, interpolation, growable lists of integer/string/bool values,
  and byte-array literals that decay to raw byte pointers.
- Explicit raw pointers, pointer arithmetic, `rawptr`, `addr`, and
  volatile raw-pointer loads/stores.
- Inline machine-code byte blocks (`asm`) with register input/output
  declarations and trusted clobber declarations.
- Hosted Linux x86-64 ELF output and freestanding output with a
  configurable entry symbol and heap-bound relocations.
- Integer constant folding and an initial Orum object-file/linker path,
  with direct-call and section-address relocations.

## Important limits and caveats

- The parser, typechecker, code generator, ELF writer, object format, and
  linker are implemented in Python; Orum is not self-hosting.
- The backend currently targets x86-64 ELF. Other architectures and
  executable formats are not implemented.
- `f32` and `f64` are recognized by the type checker but rejected by code
  generation. `array[T, N]` is parsed as a type but is not a general
  implemented value type. `[ ... ]` literals are restricted to byte
  literals, not general arrays.
- The hosted runtime uses direct Linux syscalls and a fixed 1 MiB heap;
  it is not yet a complete portable standard library.
- `take` performs source-file inclusion. Module paths are resolved from
  the importing file's directory; `compile_source` defaults to the current
  working directory, while the CLI uses the source file's directory.
  Nested imports are resolved from their own importer, each file is loaded
  at most once per compilation, and cycles are rejected. The names listed
  after `take` are not filtered: the whole module is included, so imported
  names must exist in that module and duplicate declarations can conflict.
- The Orum object format is a project-specific intermediate, not ELF
  relocatable object format. `orumc -c file.orum -o file.o` compiles one
  source file, and `orumc --link file.o helper.o -o program` links Orum
  objects into an executable. The linker resolves direct function calls
  between objects and relocations to each object's `.rodata` and shared
  heap slots in `.data`. The linker emits an entry stub that initializes
  heap bounds once; hosted object links include the string-output helper
  needed by `say(str)`. `take` is not accepted by `compile_object`, and
  the object path does not provide general external data symbols or a
  general-purpose linker.
- Function-pointer calls use the same System V calling convention as
  direct Orum calls, support at most six integer arguments, and accept
  integer/bool results. The current pointer-call ABI does not support
  non-integer arguments or other result types.
- Inline assembly is emitted verbatim; declared clobbers are trusted and
  are not validated by an instruction decoder.
- There is no complete standard library, formatter, debugger integration,
  or broad optimization pipeline yet.

## Version history in this repository

- v0.001: initial compiler, functions, control flow, structs, and basic
  native code generation.
- v0.002: string interpolation and growable lists.
- v0.003: mutable parameters and list iteration.
- v0.004: bitwise operators, explicit raw pointers, and volatile access.
- v0.005: inline machine-code byte blocks.
- v0.006: freestanding output and configurable entry symbols.
- v0.009: `addr` support for obtaining the address of a local variable.
- v0.010: byte-array literals and pointer arithmetic.
- v0.011: function-pointer types and calls.
- v0.012: integer constant folding.
- v0.013: named `share`/`take` source imports and a limited object-file
  linker with direct-call, rodata/data, and shared runtime heap support.

The checked-in release notes do not describe v0.007 or v0.008. The
source history includes an entry-symbol change in that range, but exact
release boundaries are not documented here.

## Known gaps

Module imports currently include whole files rather than selecting only
`share` declarations. Separate compilation supports the tested direct-call
and section-address relocation cases, but not general external data or
freestanding heap-symbol initialization through the executable linker.
The object format is not an ELF relocatable format. Right shifts are
deliberately not constant-folded before operand types are known, ensuring
compile-time behavior agrees
with signed versus unsigned runtime operations.

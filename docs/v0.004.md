# Orum v0.004 — Bitwise Operators & Volatile Raw Pointers

Kernel push, part 1. Local only; nothing here is pushed to any repo.

## New syntax

### Bitwise operators (binary)

| Op | Meaning | Example |
|----|---------|---------|
| `&` | bitwise and | `reg & 0xFF` |
| `\|` | bitwise or | `flags \| 0x40` |
| `^` | bitwise xor | `acc ^ val` |
| `<<` | shift left | `1 << 10` |
| `>>` | shift right | `x >> 3` |

### Bitwise not (unary)

`~x` — flips all 64 bits. `~0` is `-1`.

### Precedence (C-like, tightest to loosest)

```
unary (-, ~)
* / %
+ -
<< >>
< <= > >= == !=
&
^
|  (loosest)
```

Notes:
- `1 << 2 + 3` is `1 << (2 + 3)` = 32 (additive binds tighter than shift).
- The C gotcha is preserved: `a & mask == 0` parses as `a & (mask == 0)`
  because `&` binds looser than `==`. **Parenthesize your masks.**
- `|` is also the union operator in *type* position (`string | error`).
  The lexer emits one PIPE token; the parser decides by grammatical
  context (types vs expressions never overlap), so there is no ambiguity.

### Type rules

- All operands must be integers (`i8`–`i64`, `u8`–`u64`, `int`). Anything
  else is a compile error.
- `& | ^`: result keeps the left type when both sides match, else `int`
  (same rule as `+ - *`). Everything is a 64-bit word at runtime.
- `<< >>`: the result has the *value's* type; the shift amount's type
  never leaks into the result.
- `>>` follows signedness: arithmetic shift (`sar`, sign propagates) on
  signed types, logical shift (`shr`, zeros fill) on unsigned types.
  `<<` (`shl`) is identical for both.
- The shift count is masked to 6 bits by the hardware (`x << 70` shifts
  by 6). Negative counts use their low 6 bits. This matches x86-64 and
  is the documented semantics, not an accident.
- Constant folding understands all of this: `x: u8 = 0xF0 & 0x0F`
  compiles (0 fits); `x: u8 = 0xFF | 0x100` is a compile error (511
  doesn't fit); `x: u64 = 1 << 63` compiles (the pattern fits `u64`).

### Raw pointer dereference

`*p` desugars to `p[0]` — a zero-offset access. `*p = v` works because
the desugared index is an assignable target. Both are volatile (below).

### `rawptr(addr)`

```
p: raw *u32 = rawptr(0xF00000)
```

Materializes a `raw *T` from an integer address. The element type comes
from the annotation at the call site — calling `rawptr` without a
`raw *T` annotation is a compile error. The address must be an integer.
Deliberately explicit and dangerous-looking: integer-to-pointer
conversion is exactly what Orum wants visible.

On hosted builds the address must be valid user memory (there is no
MMIO on Linux). Real hardware addresses arrive with freestanding mode,
a later version. `examples/mmio.orum` is compile-only for this reason.

## The volatility guarantee (DECIDED, no opt-out)

**Every `raw *T` load and store is volatile.** Raw pointers exist for
hardware and MMIO. The compiler must never elide, merge, or reorder
these accesses — the hardware can change a value (or care about a
write) at any time, and only the hardware knows.

What this means concretely:
- `x = p[0]` in a loop emits a load on *every iteration* — never hoisted.
- `p[0] = 1` followed by `x = p[0]` emits both the store and the load —
  no store-to-load forwarding.
- `p[0] = 1` followed by `p[0] = 2` emits both stores — no dead-store
  elimination.

How it's enforced:
1. The typechecker stamps `node.volatile = True` on every `Index` node
   whose object is `raw *T` (including desugared `*p`). The flag is on
   the AST so every current and future pass can see it.
2. The codegen's raw load/store paths (`gen_index`, `gen_assign`) emit
   exactly one instruction per source access and carry VOLATILE comments
   marking the invariant.
3. `tests/test_v0004.py::TestVolatility` proves it: emitter call counts
   (10 lexical reads → 10 loads; store+load → both; double store →
   both) plus disassembly of the final binary proving the load sits
   inside the loop body.

There is no `volatile` keyword and no opt-out. If you hold a
`raw *T`, you opted into hardware semantics when you created it.

## What v0.004 does NOT yet do

- `and` / `or` / `not` keywords (boolean logic still via `==`/`!=`/comparisons)
- Volatile *struct field* access through raw pointers (only `p[i]` indexing)
- Freestanding target (no syscalls/brk) — the mmio example can't run yet
- Inline `asm` — next on the kernel roadmap
- Pre-existing: large `u64` literals in *unannotated* position render via
  the signed path in `say` (v0.001 limitation, unchanged)
